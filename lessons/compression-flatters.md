# Compression flatters

**Case:** after reading 18 sources, one open-source project got summarised as *"someone's already built the thing we're building."* The user pushed back: "is it really? let's deep dive." Cloning it and reading the actual operations showed it had none of our core capability. It was procedural where ours was generative, the *opposite half* of the system, overlapping exactly one of six stages.

**Why:** the README pattern-matched hard to our vocabulary, and the summary compressed on the resemblance. Nothing was fabricated. The *shape* was wrong, and a wrong shape is worse than a wrong fact because it doesn't look like an error. Summarising is lossy, and the loss isn't random: it drifts toward the tidier, more quotable claim. "Someone built our thing" is a better sentence than "someone built an adjacent thing with one overlapping stage", so it's the one that survived.

**How to apply:**
- Before a comparative claim ("X is basically Y", "this replaces that", "we already have this"), check it against the artifact: clone it, read the op list, parse the file.
- Go one level deeper than feels necessary, specifically for claims that came out tidy.
- When the deep dive contradicts the summary, lead with the correction. The user getting there by disbelieving you is the method working, not a mishap.

The tell: **the confident sentence is the one to go and check.**
