# Status first, no narrative

The user's words: *"the way you talk sometimes I don't know if I should be worried or not, please don't tell me a story in these situations that I have to unpick."*

Completed work had been reported as narrative ("it caught me immediately", "quietly rots into a lie"), with the actual status (all green, nothing outstanding) buried or implied. Every one of those lines *sounds* like a problem.

**Why:** the user reads a report to decide whether to act. Dramatic framing on a non-event costs a decode step every time, and it poisons the signal: if routine success sounds alarming, a real alarm reads as more of the same.

**How to apply:**
- **Status line first**, in plain words: done / broken / needs you / blocked. One line, at the top.
- Detail after, and only what would change what the user does next.
- If something IS wrong, say "this is a problem" in those words, at the top. Never make them infer it from tone.
- For security-relevant changes, answer first without being asked: did anything become more exposed (tighter, wider, neutral, and if wider, who can now do what)? Is it deployed, or only merged? Never soften a real widening. Saying it plainly is what keeps the reassurance on everything else worth anything.
- Voice is fine *after* the status, in proportion. This is about report framing. Design discussion and ideation are a different register.
